# Результати спринта 2

## S-16. Валідація структури вивантаження розкладу

Як адміністратор застосунку, я хочу автоматично перевіряти цілісність колонок
файлу навчальної частини, щоб зміна структури не пошкодила базу (`SC-01`).

### Рішення

Перевірка йде двома рівнями, до будь-якого запису в базу. Формат файлу описано в
`export_sample.md`.

| Рівень | Що перевіряється | Якщо не пройшла |
| --- | --- | --- |
| Структура | у заголовку є обов'язкові поля `date`, `start_time`, `group`, `room`; роздільник `;` | імпорт блокується повністю, адміністратор отримує сповіщення зі списком відсутніх полів |
| Рядок | `date` це існуюча календарна дата, `start_time` і `end_time` у форматі `ГГ:ХХ`, `end_time` пізніше за `start_time`, `group` і `room` не порожні | рядок пропускається, у лог записується номер рядка і причина, решта рядків імпортується |

Необов'язкові поля (`teacher`, `department`, `contact`) на валідацію не
впливають: їх відсутність дає порожні блоки на екрані, а не помилку імпорту.

Сповіщення адміністратору містить дату вивантаження, назву файлу і перелік
відсутніх полів. Валідатор нічого не пише в базу, тому збій структури не
торкається вже збереженого розкладу.

### Критерії приймання

| № | Якщо | То |
| :-: | --- | --- |
| A1 | у файлі є всі обов'язкові поля `date`, `start_time`, `group`, `room` | валідатор пропускає файл далі на імпорт |
| A2 | у заголовку немає хоча б одного обов'язкового поля | імпорт блокується, адміністратор отримує сповіщення |
| A3 | усі рядки коректні | імпортуються без перерв |

### Тест-кейси

| ID | Крок | Очікуваний результат | Критерій |
| :-: | --- | --- | :-: |
| TC-16-1 | подати коректний файл із `export_sample.md` | файл пройшов, усі рядки передано на імпорт | A1, A3 |
| TC-16-2 | прибрати з заголовка `start_time` | імпорт заблоковано, у сповіщенні названо `start_time` | A2 |
| TC-16-3 | прибрати одразу `group` і `room` | імпорт заблоковано, у сповіщенні обидва поля | A2 |
| TC-16-4 | замінити роздільник `;` на `,` | імпорт заблоковано як файл без обов'язкових полів | A2 |
| TC-16-5 | залишити порожній `start_time` в одному рядку | рядок пропущено й записано в лог, решта імпортується | A3 |

### Граничні випадки

- Порожній файл або файл тільки із заголовком: імпорт блокується, у
  сповіщенні вказано, що даних немає.
- Додаткове невідоме поле в заголовку: ігнорується, імпорт не блокується.
- Зміна порядку полів у заголовку не є помилкою: поля читаються за назвою.

## S-09. Імпорт розкладу з системи деканату

Як адміністратор застосунку, я хочу завантажувати розклад із системи
деканату автоматично, щоб не переносити зміни руками щотижня (`SC-01`).

### Рішення

Імпорт запускається після того, як валідатор S-16 пропустив файл. Усе
виконується однією транзакцією, тому обрив посередині не лишає половину
розкладу.

1. Валідатор S-16 перевіряє структуру і рядки.
2. Для кожного коректного рядка шукається викладач у таблиці `teacher` за
   `full_name`: якщо немає, створюється запис з кафедрою і контактом.
3. Заняття записується в `lesson`: `weekday` обчислюється з `date`, дата
   зберігається в полі `lesson.date`, група і аудиторія беруться з рядка.
4. Заняття, яке вже є в базі з тією ж групою, датою і часом початку,
   оновлюється, а не дублюється.
5. Після успішного імпорту оновлюється `sync_state.schedule_version`.
6. Рядки з помилками формату потрапляють у лог.

Формат запису в лог помилок:

```
2026-10-26 09:12:04; рядок 7; start_time порожній; рядок пропущено
2026-10-26 09:12:04; рядок 12; дата 2026-13-45 не існує; рядок пропущено
```

### Відображення полів на базу

| Поле файлу | Куди пишеться |
| --- | --- |
| `date` | `lesson.date`, `lesson.weekday` |
| `start_time`, `end_time` | `lesson.start_time`, `lesson.end_time` |
| `group` | `lesson.group_id` |
| `room` | `lesson.room` |
| `subject` | `lesson.subject` |
| `teacher` | `teacher.full_name`, зв'язок `lesson.teacher_id` |
| `department` | `teacher.department` |
| `contact` | `teacher.contact` |

### Критерії приймання

| № | Якщо | То |
| :-: | --- | --- |
| B1 | подано коректний файл вивантаження | парсер зчитує його без помилок |
| B2 | файл містить дисципліни, викладачів і аудиторії | дані оновлюються в базі розкладу |
| B3 | запис має некоректний формат | у лог записується помилка, система не падає |

### Тест-кейси

| ID | Крок | Очікуваний результат | Критерій |
| :-: | --- | --- | :-: |
| TC-09-1 | імпортувати файл із `export_sample.md` | 4 заняття в `lesson`, лог порожній | B1 |
| TC-09-2 | перевірити викладачів після TC-09-1 | у `teacher` два записи, у другого порожній контакт | B2 |
| TC-09-3 | повторно імпортувати той самий файл | кількість занять не зросла, записи оновлено | B2 |
| TC-09-4 | імпортувати файл з рядком з неіснуючою датою | рядок у лозі з номером, решта занять імпортована | B3 |
| TC-09-5 | обірвати імпорт посеред файлу | у базі лишається попередня версія розкладу | B2, B3 |

### Граничні випадки

- Заняття без викладача (порожні `teacher`, `department`, `contact`):
  записується з порожнім `teacher_id`.
- Зміна аудиторії в наступному вивантаженні: заняття оновлюється, стара
  аудиторія не лишається.
- Файл, який видаляє заняття, що були раніше: у цій версії не обробляється.
