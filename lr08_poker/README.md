## 1. Формат і масштаб

| Поле | Значення |
| --- | --- |
| Дата оцінювання | 2026-10-18 |
| Формат | Триточкова оцінка (одноосібно): три ролі — `optimistic`, `likely`, `pessimistic` по кожній історії; для 4 складних сторій — другий раунд після конверт-1 |
| Інструмент | Фізичні картки Fibonacci + Google Sheets для розрахунку PERT |
| Історія-еталон, яку назвали 3 | S-09 «Перегляд деталей обраної пари» — чітко визначена функціональність з мінімальною невизначеністю |
| Скільки історій оцінено | 9 (усі історії REL-1) |

Чому саме ця історія стала якорем: S-09 є однорідним та атомарним завданням — відобразити структуровану картку з деталями пари (назва, час, аудиторія, викладач) з готової моделі даних, що вже реалізована в S-02; оцінка 3 SP слугує орієнтиром «мала, але не тривіальна» для всіх інших порівнянь.

Що саме міряють ваші points: Story points вимірюють **відносну складність і невизначеність** реалізації, а не астрономічний час у годинах — 1 SP відповідає дрібній, добре зрозумілій задачі, 13 SP — великій з суттєвими технічними ризиками.

## 2. Історії з найбільшим розкидом

| story_id | O і P першого раунду | Що створює невизначеність | Підсумок PERT |
| :-: | :-: | --- | :-: |
| S-04 | O=5, P=13 | Невідомий API push-сповіщень Android 13+, вимоги дозволів від ОС, архітектура серверного diff-движка | 13 SP |
| S-02 | O=3, P=8 | Невідомий формат і стабільність публічного API розкладу академії, обсяг adapter-шару та обробки помилок | 8 SP |
| S-06 | O=3, P=8 | Стратегія TTL-інвалідації SQLite-кешу, UX-стан «дані застаріли», вирішення конфліктів синхронізації | 8 SP |
| S-03 | O=3, P=8 | Жести свайпу між тижнями, інвалідація кешу при зміні дати, edge-case початку/кінця навчального семестру | 8 SP |

Що з цим робити до початку роботи: Для S-04 необхідно до старту спринту провести технічний spike тривалістю 2–3 дні — реалізувати мінімальний прототип push-дозволів на Android 13+, що дозволить підтвердити або спростувати песимістичну оцінку. Для S-02 потрібно за перший тиждень закінчити T-02 (специфікація API) і перевірити реальний формат ендпоінту академії, після чого уточнити оцінку перед початком T-06.

## 3. Конверт 1: переоцінка після нової інформації

| Поле | Значення |
| --- | --- |
| Історія | S-04 «Сповіщення про зміни в розкладі» |
| Чому саме вона | Найбільший розкид раунду 1 (O=5, P=13 — різниця 3 карти на шкалі Фібоначчі); правило конверту: якщо песимістична оцінка більш ніж удвічі перевищує оптимістичну, розкид несе приховану технічну невизначеність |
| Оцінка до конверта | 8 SP (PERT раунду 1: O=5, M=8, P=13 → 8.33 → 8) |
| Оцінка після конверта | 13 SP (PERT раунду 2: O=8, M=13, P=21 → 13.5 → 13) |

Що змінилось: Конверт розкрив вимогу Android 13+ запитувати явний дозвіл `POST_NOTIFICATIONS` в runtime через системний діалог ОС, що додає окремий UI-флоу onboarding для нових установок та обробку відмови користувача.

Кого ще це стосується: S-07 («Відображення поточної та наступної пари») теоретично залежить від аналогічного дозволу для планування фонового оновлення, але S-07 сам по собі обмежується тільки UI без фонових воркерів — відображення пари відбувається лише при відкритому застосунку, тому оцінка S-07 залишається 2 SP незмінною.

## 4. Сума першого релізу проти ємності варіанта

| Що | Значення |
| --- | --- |
| Сума `final_estimate` історій `REL-1` | 50 SP |
| Ємність спринта мого варіанта (V07) | 10 SP |
| Спринтів до строку релізу | 5 (10 тижнів ÷ 2 тижні на спринт) |
| Місткість (ємність × спринти) | 50 SP |
| Різниця | 0 SP |

Що я бачу: Сума оцінок рівно збігається з місткістю п'яти спринтів (50 SP = 50 SP) — план «впритул», без буфера на непередбачені ускладнення та технічний борг. Перший спринт матиме вищий ризик недовиконання через spike-дослідження push API і невідомий формат даних академії.

Що робитиму, якщо не влазить: Якщо після першого спринту фактична velocity виявиться нижче 10 SP (що дуже імовірно з огляду на технічні ризики S-04), до REL-2 перенесу S-04 (push-сповіщення, 13 SP) і S-03 (навігація між тижнями, 8 SP) — залишивши у першому релізі лише базовий перегляд розкладу (S-02, S-09, S-06, S-05, S-07, S-08, S-16 = 29 SP за 3 спринти).

## 5. Конверт 2: відповідь замовнику про години

Шановний замовнику, відповідь на питання «скільки це коштує в годинах і гривнях» буде готова на наступному тижні після завершення технічного spike для S-04 та погодження специфікації API (T-02). Переводити Story Points безпосередньо в години зараз некоректно: ми маємо лише один завершений спринт симуляції з якого неможливо виводити достовірний показник velocity. Конкретне число у гривнях з'явиться в бюджетному розрахунку ЛР16 після закриття двох спринтів (ЛР03, ЛР09) та уточнення rate-карт ролей. Ставка PM, BA, Dev та QA по варіанту V07 зафіксована у бюджеті проєкту (480 000 UAH стеля прямих витрат).

## 6. Історії з карткою «не розумію»

Картка «?» у жодному раунді оцінювання не з'явилась — усі дев'ять сторій REL-1 мали достатньо деталізовані Acceptance Criteria після ЛР06, щоб дати числовий голос з першого раунду. Найбільша початкова невпевненість була по S-04, але навіть тоді дискусія зводилась до вибору між 8 та 13, а не до відмови від оцінки. Це підтверджує якість DoR: жодна сторія не взята в спринт без чітких критеріїв приймання.

## 7. Що я зрозумів про свій беклог

Оцінювання виявило ключовий ризик для першого релізу: **дві найбільші сторії (S-04, 13 SP, та S-02, 8 SP) блокують або суттєво впливають на решту семи** — S-04 потребує серверного diff-движка, якого немає в жодній іншій сторії, а без базового вивантаження розкладу (S-02) неможливо реалізувати S-09, S-03, S-05, S-06, S-07, S-08 та S-16. Разом S-04 та S-02 становлять 42% суми REL-1 (21 з 50 SP). Практичний висновок: перший спринт має бути сфокусований виключно на S-02 плюс spike для S-04, інакше решта команди буде заблокована на другому тижні.
