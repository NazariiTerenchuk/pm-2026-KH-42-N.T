## 1. Стеля годин мого варіанта

| Роль | Зайнятість | Годин до релізу | Скільки взяв у WBS |
| --- | :-: | ---: | ---: |
| PM | 25% | 100 | 70 |
| BA | 50% | 200 | 170 |
| Dev | 100% | 400 | 380 |
| QA | 25% | 100 | 100 |
| **Разом** | **200% (2.0 FTE)** | **800** | **720** |

Розрахунок: сумарна зайнятість ролей 2.0 FTE × 10 тижнів до першого релізу × 40 робочих годин на тиждень дає 800 годин робочого часу команди. У корені `wbs.csv` (вузол `1`) закладено 720 годин, що становить 90.0% від встановленої варіантом стелі.

Чому саме стільки: 720 годин (90%) дозволяють покрити весь критичний функціонал першого релізу (MVP) і одночасно залишити резерв у 80 годин (10% загального фонду робочого часу). Цей нерозподілений резерв закладено як управлінський буфер на покриття технічних ризиків, пов'язаних із нестабільністю публічного формату даних розкладу академії та потенційними правками на етапі приймального тестування (UAT).

## 2. Правило 100%: як перевіряли

Спосіб перевірки: деревоподібне агрегування трудовитрат знизу вгору (Bottom-Up calculation). Кожен проміжний вузол WBS дорівнює точній сумі годин своїх дочірніх пакетів, що підтверджено валідатором (правило WBS-3):
- Вузол 1.1 «Управління проєктом»: 40 + 30 = 70 год.
- Вузол 1.2 «Аналіз вимог та проєктування UX»: 80 + 90 = 170 год.
- Вузол 1.3 «Розробка програмних компонентів»: 40 + 110 + 130 + 100 = 380 год.
- Вузол 1.4 «Забезпечення якості та валідація»: 60 + 40 = 100 год.
- Корінь 1: 70 + 170 + 380 + 100 = 720 год.
Жодна активність не дублюється між гілками декомпозиції (кожен результат закріплений за одним робочим пакетом та однією відповідальною роллю).

Робота, яку ледь не забули:
1. Налаштування середовища збірки та конвеєра CI/CD (пакет 1.3.1) — технічна основа, без якої неможливі регулярні автоматизовані білди застосунку.
2. Серверний фоновий сервіс виявлення змін у розкладі (пакет 1.3.4) — користувачі бачать лише push-повідомлення у смартфоні, проте для їх генерації необхідний періодичний фоновий порівняльний аналіз структури розкладу на сервері.
3. Організація та проведення приймального тестування (UAT) безпосередньо зі стейкхолдерами ST-01 та ST-03 (пакет 1.4.2) — процес валідації критеріїв успіху SC-01..SC-03 вимагає виділеного часу QA та стейкхолдерів.

Що свідомо поза обсягом (синхронізовано зі статутом `lr05_charter/README.md`):
- Власна повноцінна веб-панель диспетчера деканату для ручного внесення розкладу (використовуємо адаптер-парсер до чинного серверного веб-джерела академії).
- Інтерактивна 2D/3D-карта корпусів та прокладання пішохідних маршрутів між аудиторіями (відкладено на REL-2/REL-3).
- Мобільний клієнт під операційну систему iOS (перший реліз сфокусовано виключно на Android для покриття більшості студентів та економії бюджету на ліцензіях Apple Developer).
- Облік відвідуваності занять та електронний журнал оцінок (належить до компетенції окремої системи деканату).

## 4. Критичний шлях

Дата старту робіт: 2026-10-19 (понеділок). Робочий тиждень — 5 днів (субота та неділя не враховуються).

| Що | Значення |
| --- | --- |
| Критичний шлях, робочих днів | 48 |
| Ланцюг критичних робіт | T-02 → T-04 → T-05 → T-08 → T-09 → T-10 → T-11 → T-12 |
| Дата завершення за планом | 2026-12-23 |
| Строк мого варіанта, робочих днів | 50 (10 тижнів × 5) |
| Різниця | -2 робочих дні (48 - 50) |

Чи вкладаємось: **Так**, критичний шлях у 48 робочих днів повністю вкладається у встановлений варіантом V07 ліміт у 50 робочих днів (10 тижнів), забезпечуючи резерв у 2 робочих дні перед дедлайном семестру (2026-12-25).

Що з цим робимо:
Початкова консервативна декомпозиція з послідовним ланцюгом розробки (T-06 парсер → T-08 UI → T-09 push) давала сумарну тривалість 60 робочих днів (перевищення ліміту на 10 днів / 2 тижні).
Для забезпечення вчасного релізу було ухвалено управлінське рішення застосувати метод швидкого проходу (fast-tracking): розробку мобільного клієнтського інтерфейсу (T-08) розпаралелено з розробкою бекенд-парсера (T-06) на базі узгодженої на вісі T-05 специфікації API з використанням mock-даних. Також паралельно зі стартом вимог запущено розгортання CI/CD (T-01). Завдяки цьому критичний шлях скорочено до 48 днів без урізання скоупу першого релізу.

Робота з найбільшим резервом:
Найбільший резерв мають управлінські задачі PM (T-03 та T-07, резерв по 39 робочих днів), оскільки вони забезпечують координаційний супровід і безпосередньо не затримують розробку коду. Серед технічних робіт найбільший резерв має налаштування інфраструктури CI/CD (T-01, резерв 10 днів), а розробка серверного парсера (T-06) має резерв 2 дні відносно клієнтського інтерфейсу T-08.

## 7. Робочий журнал

Під час декомпозиції робіт було переглянуто декілька початкових припущень:
1. Залежність між бекенд-парсером розкладу (T-06) та клієнтським застосунком (T-08) спочатку розглядалася як жорстка Finish-to-Start. Проте розрахунок показав, що послідовне виконання призводить до критичного шляху у 60 днів. Проблему вирішено архітектурно: створення контракту API та мок-сервера на етапі T-05 дозволило розробляти інтерфейс незалежно.
2. Відокремлено специфікацію вимог (T-02, BA) від тестування (T-10, QA): залучення QA на етапі T-10 та T-11 забезпечує незалежну валідацію за критеріями успіху SC-01..SC-03.
3. Усі 10 листових вузлів WBS отримали пряме відображення в календарному плані schedule.csv, що гарантує відсутність незапланованої чи «забутої» роботи.
